# Agent 不确定时找用户确认

Agent 在任务执行中遇到**任何不明确的地方**，都必须停下来用 `AskUserQuestion` 或 `NotifyUser` 明确向用户确认，**不能**凭经验猜测、也不能用注释"TODO 后续确认"跳过、更不能按"常用默认值"自行决定。

## 触发时机

以下**任一**情形出现就必须触发确认，不要等：

1. **需求有歧义**：用户描述模糊（"改一下"、"稍微"、"差不多"）、遗漏关键参数（阈值、窗口、时间范围、覆盖的页面/标的类型）、或同时出现两条可能冲突的路径（如"既要 A 也要 B"但 A/B 不能同时满足）。
2. **实现路径多选**：有 2 种以上可行实现方式，选择会影响行为（如：改 appConfig 默认值 vs 在业务文件内硬编码；改 worker 输出结构 vs 主线程补算）。
3. **口径冲突**：现有代码/配置/文档中对同一问题有两处不同说法（如"默认 365 天"在 A 文件写的、B 文件写的是 300 天）。
4. **边界条件不明确**：参数为 null/undefined/空数组/长度为 0 时怎么处理；越界/负收益/极端值时怎么兜底。
5. **用户意图需反证**：任务描述的实现方向有明显风险（如"改 as-of 窗口为 6 个月"，但项目约定窗口至少 120 个月），需要先解释风险再让用户决定要不要继续。
6. **破坏性改动**：改动会影响已缓存的数据、已存的表格列、历史导出结果的列顺序或口径（破坏性变更清单见 `code-change-skill-sync`）。
7. **涉及外部副作用**：改 HTTP 接口签名、改 API 路径、改 Worker 消息协议 —— 调用方是否知晓、需要同步更新哪些方。

**不触发**：纯问答（"这段代码做什么"）、纯排查（"为什么报错"，且报错原因已明确定位、修复路径唯一）、代码阅读、用户直接给了完整规格的实现任务（"按 XX 接口签名新增 Y 函数"）。

## 确认方式

- **多选场景 / 二选一决策**：用 `AskUserQuestion`，给出 2~4 个选项，每个选项用一句话说明**行为差异**和**可能影响面**，默认选项目推荐的路径。
- **参数 / 阈值填数字**：用 `AskUserQuestion` 的"Other"选项让用户直接输入，或在选项里给出 2~3 个常用候选（如 120 / 60 / 240 月）。
- **风险提示**：先解释"这样做会有什么后果"，再问"要不要继续"。
- **多轮澄清**：一次 `AskUserQuestion` 最多 4 个选项，问题超过 4 个时分两轮，不要合并成一个很长的多选。

## 确认内容必须包含

- **上下文**：为什么这个地方不明确，不是什么都问。
- **选项含义**：每个选项会导致什么具体行为变化，不要用"方案 A"、"方案 B"这种抽象说法。
- **推荐理由**：明确告诉用户你推荐哪个、为什么（如"选项 A 走 config 集中入口、选项 B 在业务文件硬编码，推荐 A 因为 AGENTS.md 约定跨页面复用参数必须集中到 appConfig"）。
- **影响面**：会影响哪些文件/页面/导出/缓存键/历史结果。

## 确认后

- 用户做出选择后**立即**推进实现，不要回头再问同一个问题。
- 用户选择的结果在最终回复中明确说明（"按你选的方案 X，改了 Y 文件"）。
- 如果用户的选择违反项目约定/有已知风险，按"风险提示"模式**先说明**再执行，执行后在最终回复中明确标注风险点。

## 禁止

- 不说任何话就自行决定 —— 必须显式触发确认。
- 用"假设 / 暂定 / 按惯例 / 默认值"这类词绕过确认。
- 合并多个不相关的问题成一个很长的"你确认一下这个这个那个那个"的多选。
- 明明有歧义但为了快而跳过确认 —— 先停下来问再写代码。
